# 10 — Plan

## The shape of the change

A storage pair, one new pure fact about a date, and a marker plus a control hung off the grid this
module already has.

```
already there                              new
──────────────                             ───
settings.ts (registration + accessors) ─▶  SETTINGS.dayNotes, getDayNotes/setDayNotes
clock.ts (worldTimeAtDate, monthShape) ─▶  dayKeyAt(year, month, day)     ┐
                                                                          ├─▶ notes.ts (noteFor/setNote/clearNote)
month-grid.ts (monthView)              ─▶  MonthDay.hasNote              ┘
calendar-bar.ts (#monthGrid, #onClick) ─▶  the marker, the edit-note control, the click case
weather-override.ts (the pattern)      ─▶  day-note.ts (new modal, same shape)
```

Nothing here is new machinery. It is the same "facade over existing arithmetic, then markup" shape as
round 09, applied to a `dayKey` instead of a world time.

## Key decisions

**`dayKeyAt` skips `WorldDate` entirely.** `worldTimeAtDate` exists because moving the clock needs a
world time; a note only ever needs the key, and `dayKeyFor` never depended on the time of day. Routing
through `getWorldDate(worldTimeAtDate(...))` the way the heading currently resolves a festival would
work, but it is a resolve-then-discard round trip through arithmetic the key does not need, called once
per grid cell rather than once per selection.

**The notes map is passed into `monthView`, not read inside it.** Same discipline as `today` and
`selected`: a pure function that took a dependency on `game.settings` would need a settings mock in
every test that touches it, for state that is trivial to hand in as a plain object.

**One setting for the whole map, not one per day.** `weatherEffectMap` and `weatherOverride` already
establish that shape in this codebase, and a per-day setting would need registering (or an unregistered
world-data write) per day, which Foundry's settings API is not built for. The rewrite-everything cost
this implies is named in the spec as an accepted property, not solved here.

**The modal is a function, not an `ApplicationV2` subclass.** `weather-override.ts` already proved the
`DialogV2.wait` shape is enough for "one form, one or two buttons, closes on save." A day note needs
one field instead of three; nothing about it asks for more machinery than that file already has.

**Escaping goes in `day-note.ts`, at the one point text crosses into HTML.** The current note's text
becomes a `<textarea>` default value inside a template string, the same way `weather-override.ts`
builds its form — but that file only ever interpolates numbers and enum values, never arbitrary text.
A GM's own note containing `<`, `&` or a quote must not be able to break out of the textarea or the
surrounding markup, so the value is escaped before it is interpolated, and nowhere else needs to be:
the grid only ever renders presence as a CSS class, never the text itself.

## Tests

| Test | Guards |
| --- | --- |
| `clock.test.ts` | `dayKeyAt` matches `getWorldDate(worldTimeAtDate(y, m, d)).dayKey` for both backends, including a calendar with months of its own |
| `month-grid.test.ts` | `hasNote` is true only for the day whose `dayKey` is a key in the map passed in; false for every other day in the same month; false for a key present but blank |
| `calendar-bar.test.ts` | `edit-note` is absent for a player and absent until a day is selected; present only on the selected cell; a cell whose `dayKey` is in the notes map carries `kronos-has-note`; clicking `edit-note` does not call `advance` |

The last one matters for the reason round 09's equivalent guard did: `edit-note` sits right next to
`go-to-day` on the same cell, and the way this regresses is somebody wiring it to the same action by
copy-paste.

Each new assertion is watched failing before it is trusted, as in the previous rounds.

## Verification

`npm run check`, then the harness:

- a day with a note shows the marker at all three sizes, and a day without one does not
- the selected cell shows both controls without overflow at the small size — the spec's first open
  question, decided by measurement
- opening the modal on a day with an existing note shows that text; saving new text and reopening the
  grid shows the marker; deleting removes it
- saving whitespace-only text leaves no marker
- a note's text containing `<` and `&` round-trips through the modal without breaking it
