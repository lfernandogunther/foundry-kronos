# 09 — Plan

## The shape of the change

Less than the roadmap implied. The arithmetic is already in the repository — it was written for the step
and jump controls — and what is missing is a facade over it plus the view.

```
already there                          new
─────────────                          ───
reckoning.worldTimeAt(y,m,d,secs)  ┐
pf2e-clock.utcMsToWorldTime(ms)    ├─▶ clock.worldTimeAtDate(...)   ─┐
gregorian.daysInMonth(y,m)         ┘                                 ├─▶ month-grid.ts (pure shape)
reckoning.describeWorldTime(...)   ───▶ clock.monthShape(y,m)        ┘         │
                                                                              ▼
                                                                    calendar-bar renders it
```

Two functions in `clock.ts`, one pure module for the month's shape, and markup. The same split as the
timeline: the geometry is testable without a DOM, the render function is markup.

## Key decisions

**`monthShape` returns the blanks, not the renderer.** How many empty cells precede day 1 is arithmetic —
the weekday index of day 1, modulo the weekday count — and it is exactly the thing the reference got
wrong. Computing it where it can be tested is what stops us shipping decorative columns.

**Both new functions take and return the *displayed* year.** `yearOffset` is applied on the way out of
`describeGregorian`, so the inverse has to subtract it. Getting this wrong shows up as a grid 2700 years
away from the bar, which is obvious — but it is obvious only if something renders, and a test says so
first.

**Selection lives on the application, not in a setting.** It is per-view state that means nothing after a
reload, so it is a private field like the drag offset. Two GMs do not share a selection.

**Time moves through the same `advance` path as everything else.** The go-to-day control computes
`worldTimeAtDate(...) - game.time.worldTime` and hands it to `advance`, which already short-circuits zero
and refuses for a non-GM. No second route to moving the clock.

**The grid re-renders with the panel.** No separate lifecycle: the clock ticks, the panel rebuilds, the
grid rebuilds with it. Today's marker is derived at render, and the month being viewed is the one piece of
state that survives — held on the application, defaulting to the current month, and reset when the
calendar changes.

## The month being viewed, precisely

One field: an offset in months from the current month, or null for "follow the clock".

- Opening sets it to null.
- An arrow sets it to an absolute year and month.
- While null, the heading follows the clock across a month boundary.
- While set, it does not.

That is what makes the decision in the spec — follow only if showing the current month — a property of
one nullable field rather than a comparison done in three places.

## Tests

| Test | Guards |
| --- | --- |
| `clock.test.ts` | `worldTimeAtDate` round-trips against `getWorldDate` for both backends, keeps the time of day, applies the era offset, and handles a year before the epoch. `monthShape` gives 28 and 29 days for February in the right years, Tarlan's own lengths, and the leading blank count |
| `month-grid.test.ts` | Day 1 sits under its own weekday; the blanks before it equal that weekday's index; the cell count equals the month's length; today is marked only in the month it falls in; a selection past the end of a shorter month is dropped |
| `calendar-bar.test.ts` | The button and the grid are absent for a player; the grid is absent until toggled; a day cell carries a select action and **not** a step or set-time action; only the go-to-day control carries the action that moves time |

That last one is the guard that matters most. The decision this round turns on is that clicking a day
does not move the world, and the way that regresses is somebody wiring the cell to the existing
`set-time` action because it is right there.

Each new assertion is watched failing before it is trusted, as in the previous rounds.

## Verification

`npm run check`, then the harness:

- both bundled calendars, checking day 1 lands under the right weekday against a date whose weekday is
  known independently
- February 2024 and 2025, for 29 and 28
- the three sizes, measuring cell width and overflow rather than eyeballing them — this is the spec's open
  question and it decides whether the grid survives small
- a click on a day, confirming `advance` is not called
- the go-to-day control, confirming exactly one call and the right delta
